## Content

### Context

lucid-memories は、Cursor IDE（フックイベント発火・プロンプト注入）、AI エージェント（MCP ツール群）、およびローカル推論基盤（Ollama 埋め込み API）など複数の外部システムと密接に連携する。

外部システムとのインターフェース（外部 IF）仕様をどのように管理・配置すべきかについて、専用ディレクトリ（`docs/interfaces/`）の新設を伴うスキーマ拡張（案2）か、既存の仕様階層（`docs/specifications/`）に集約する方針（案1）かの検討が必要となった。

### Decision

外部 IF の仕様管理として**案1（既存の仕様階層への集約とタグ運用）を採用**し、以下の階層マッピングで管理する。また、将来的な専用ディレクトリ新設（案2）は選択肢として保留（On-hold）する。

1. **外部アクターの定義 (`docs/actors/ACT-xxxx.md`)**:
   - 連携相手となる外部システム（Cursor IDE、Ollama 等）の役割・責務・相互作用を定義する。
2. **インターフェース契約の定義 (`docs/specifications/SPEC-xxxx.md`)**:
   - 外部 IF の具体的な通信プロトコル、入出力スキーマ、エラー表現、制約（タイムアウト、UTF-8 保証など）を `SPEC` として記述する。
   - メタデータタグとして `tags: [interface, external, <対象名>]`（例: `[interface, external, hook]`、`[interface, external, mcp]`、`[interface, external, ollama]`）を付与し、内部モジュール仕様と明確に識別・検索可能とする。
3. **外部接続アーキテクチャの定義 (`docs/design/DSN-xxxx.md`)**:
   - ヘキサゴナルアーキテクチャ（ポート＆アダプタ）に基づき、外部通信障害に対するリトライ、タイムアウト、フォールバック機構、および依存性逆転の設計を記述する。
4. **提供 IF（Inbound）と利用 IF（Outbound）の扱い**:
   - 自システムが提供する IF（Hook 受信、MCP Server、Web API）は完全な入出力契約を `SPEC` に定義する。
   - 外部システムが提供する IF（Ollama API 等）は、本システムが依存するサブセットおよびエラー変換契約を `SPEC` に定義する。

### Consequences

- 新たなスキーマ種別やディレクトリを追加することなく、既存の `scripts/validate_docs.py` による検証枠組みを維持したまま外部 IF 仕様を一元管理できる。
- `SPEC` の標準見出し（`### Contract`、`### Inputs`、`### Outputs`、`### Errors`、`### Constraints`）が、外部 IF 仕様書（ICD: Interface Control Document）の標準項目と完全に一致するため、記述の抜け漏れを防ぎ高い品質を確保できる。
- プロジェクト規模の拡大や外部連携の大幅な増加に伴い、外部 IF 仕様の独立一覧性が強く求められるフェーズに至った場合は、案2（`docs/interfaces/` 新設）への移行を再検討する。
