## Content

### Context

lucid-memories の開発では `docs/` 配下で要求（NEED）、要件（REQ）、仕様（SPEC）、設計（DSN）の厳格な階層管理と自動検証（`scripts/validate_docs.py`）を導入している。しかし、システム自体の存在目的（Purpose）やシステム境界（System Boundary: In-Scope / Out-of-Scope）を明文化した正本が存在しなかった。

そのため、リポジトリ構成の整理やセットアップスクリプトの配置変更といった「開発運用・リポジトリ構成管理のタスク（Chore / Refactoring）」が、ソフトウェアの振る舞いや品質を定義する「システム要求（NEED）」として起票され、過剰なV字モデルへの落とし込みや同語反復（トートロジー）が発生していた。

システム開発論として健全な開発ガバナンスを維持するため、システム境界および要求判定基準を `docs/` 配下に定義・配置する方針の決定が必要となった。

### Decision

以下のハイブリッド方針（案Aの即時採用および案Cの将来検討保留）を採用する。

1. **案Aの採用（即時導入）**:
   - `docs/SYSTEM_OVERVIEW.md` を `docs/` ディレクトリ直下に作成・配置する。
   - 本書にシステムの存在目的、システム境界（In-Scope / Out-of-Scope）、およびタスクがシステム要求（NEED / REQ）か構成管理（Chore / ADR）かを判別する判定基準（マトリクス・フローチャート）を定義する。
   - `scripts/validate_docs.py` は `docs/*/*.md` のみを対象とするため、既存のスキーマ検証を破壊せずに即座に正本として運用を開始する。

2. **案Cの保留（将来拡張の選択肢として維持）**:
   - ドキュメント体系の成熟に伴い、将来的にスキーマ定義（`docs-document-schema.mdc`）およびバリデータ（`scripts/validate_docs.py`）を改修し、最上位階層として `docs/vision/`（`VIS-xxxx`）等を新設する選択肢を破棄せず保持（On-hold）する。

### Consequences

- 開発者および AI エージェントが、改修指示に対して「システム要求（NEED / REQ）」か「リポジトリ構成管理（Chore / ADR）」かを客観的に判定できるようになり、不要な要求文書の乱立や同語反復を抑制できる。
- 既存の CI・ドキュメント検証パイプライン（`validate_docs.py`）に一切の影響を与えず、即座にガバナンス基準を共有・運用できる。
- 将来スキーマを拡張する場合でも、`docs/SYSTEM_OVERVIEW.md` の定義をそのまま正本データとして移行・昇格させることが可能となる。
