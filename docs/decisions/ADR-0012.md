## Content

### Context

`semantic_search`（`vsearch`）は SQLite に格納された float32 BLOB ベクトルを全件読み出し、Python でコサイン類似度を計算する O(n) 実装である。Windows ポータビリティと埋め込みモデル変更の柔軟性を優先した意図的な選択だが、知識件数の増加に伴いレイテンシが線形に悪化する。

768 次元 × 4 バイト ≒ 3 KB/件。active 知識 2,000 件で約 6 MB のスキャンが 1 クエリあたり発生する見込み。

### Decision

**当面はネイティブベクトル索引（sqlite-vec 等）を導入せず、現行 O(n) スキャンを維持する。** 代わりにソフトリミットと監視で運用する。

1. **ソフトリミット**: active かつ faded/archived 以外のインデックス済み知識が **2,000 件** を超えたら `embedding_status` が `warning` を返す。
2. **監視フィールド**: `embedding_status` に `indexed_count`（既存）と `last_search_ms`（直近 `semantic_search` の経過ミリ秒）を返す。
3. **受入目標（非機能）**: インデックス済み active 知識 2,000 件以下の環境で `vsearch` p95 < 300 ms（ローカル Ollama 埋め込み生成時間を除くスキャン部分）。
4. **エスカレーション条件**: 2,000 件超が恒常的、または p95 が 300 ms を超える場合は、FTS プリフィルタ（上位 50 件に絞ってからベクトル比較）または sqlite-vec 導入を別 ADR で検討する。

Ollama 未稼働時の `embedding_unavailable` フォールバック（FTS のみ）は既存挙動を維持する。

### Consequences

- 追加依存なし。実装は `embedding_status` の拡張と `semantic_search` の計測ログが主となる。
- 2,000 件超はエラーではなく警告。運用者は prune / archive / 将来の索引導入で対処する。
- 10,000 件超の大規模利用は本 ADR の想定外。要件が出た時点で ADR を supersede する。
