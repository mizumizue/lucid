## Content

### Decision

workspace 種別 persona は `core/workspace_persona.py` に集約し、既存 `core/persona.py` の global persona 読み込み・予算見積もり関数を再利用する。`persona.get_injection()` は workspace root を受け取り、内部で `workspace_persona.compose_injection()` を呼ぶ。

### Structure

- **`persona/types/*.json`**: 種別テンプレート（sections 配列）。setup が既定 5 種（app-dev, infra, notes, research, meta）を生成。
- **SQLite `workspace_persona_bindings`**: workspace_root → type_id, status（pending / confirmed）, rationale, confidence, proposed_by, timestamps。
- **SQLite `workspace_persona_overlays`**: workspace_root → sections_json。
- **SQLite `workspace_persona_binding_events`**: propose / confirm / reject / override の監査ログ。
- **`infer_workspace_type()`**: workspace 内の既知マーカー（pyproject.toml, package.json, docker-compose, lucid-memories 等）から Agent 提案用のヒントを返す。確定は行わない。

### Data Flow

1. Agent が初回 `persona_workspace infer` で種別候補を取得し、`propose` で pending binding を記録する。
2. ユーザーが `confirm` すると status が confirmed になり、以降の hook 注入対象となる。
3. `beforeSubmitPrompt` が workspace root を渡し、`compose_injection()` が global → type → workspace の順で sections を予算内合成する。
4. ユーザーが `override` または `overlay_set` すると overlays / binding を更新し、`binding_events` に履歴を追記する。

### Trade-offs

- 種別テンプレートを JSON ファイルに置くことで、ダッシュボード未実装でも CLI / 手編集で調整できる。
- binding 状態を SQLite に置くことで workspace 横断の一覧・監査が可能。persona 自己学習テーブルとは分離し、誤自動適用を防ぐ。
- 推論はヒューリスティックのみとし、LLM 分類は Agent 側の責務とする（lucid は propose / confirm の永続化と注入に専念）。
