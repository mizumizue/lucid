# lucid-memories システム概要と境界定義書 (System Overview & Boundary)

本書は、`lucid-memories` システムの存在目的、システム境界（In-Scope / Out-of-Scope）、および開発指示が「システム要求」か「プロセス・構成管理（Chore / Refactoring）」かを客観的に判別するための判定基準を定義する正本である。

---

## 1. システムの目的とビジョン (Purpose & Vision)

**lucid-memories** は、Cursor 上で自律稼働する複数の AI エージェント間で、セッションやワークスペースを横断して知識・文脈・状態を安全かつ省トークンで永続化・想起・共有するためのローカル完結型記憶基盤である。

### 解決する課題
1. **セッション間の文脈喪失**: エージェントのチャットセッション終了やコンパクションによって、獲得した知見や決定事項が失われる。
2. **トークン消費の爆発**: 会話ログ全文をコピー・再送すると、コンテキストウィンドウが圧迫され、LLM の推論精度が低下する。
3. **データ主権とプライバシー**: 開発中のコードや設計情報を外部クラウドに送信することなく、機密性を保ちながら記憶を保持する必要がある。

### コア提供価値
- **構造化記憶 (Structured Knowledge & Map)**: 全文複製ではなく、抽出された「知識（Facts）」と「関係性（Ontology Graph）」を保存する。
- **動的ペルソナ & 省トークン注入**: プロンプト送信前に、関連度の高い記憶とペルソナを厳格なトークン予算（Token Budget）内で自動注入する。
- **Auto / Ask 権限分離**: 想起や検索は自動で行い、確定・禁止・アーカイブなどの不可逆操作は必ずユーザーの承認を要求する。
- **完全ローカル完結**: SQLite、Ladybug DB、ローカル埋め込み（Ollama）を用いて開発者マシン内で処理を完結させる。

## 2. システム境界 (System Boundary)

要求工学に基づき、開発作業や要求分析の対象が「システム内部の要求」か「システム外部のプロセス・管理タスク」かを以下のように明確に分離する。

```text
┌─────────────────────────────────────────────────────────────────────────────┐
│ 【システム外部 (Out-of-Scope)】 プロセス・環境・リポジトリ管理の関心事     │
│                                                                             │
│  - Git リポジトリのディレクトリ構成・ファイル配置                           │
│  - セットアップスクリプト（setup.sh, setup.ps1 等）の配置場所や撤去         │
│  - 文書管理スキーマ（validate_docs.py 等）や開発プロセス規律               │
│  - CI パイプライン・テストランナーの設定                                    │
│                                                                             │
│  ┌───────────────────────────────────────────────────────────────────────┐  │
│  │ 【システム内部 (In-Scope)】 実行時ソフトウェアの振る舞い・品質・契約   │  │
│  │                                                                       │  │
│  │  [外部インターフェース層]                                             │  │
│  │   - Cursor Hooks (IPC / JSON-stdio) によるプロンプト検知と注入        │  │
│  │   - MCP Server (JSON-RPC) による 20+ 個のエージェント向けツール API   │  │
│  │   - CLI による直接対話・管理操作                                      │  │
│  │   - Web Dashboard (HTTP / REST / UI) による想起・オントロジーの可視化 │  │
│  │                                                                       │  │
│  │  [コア処理層]                                                         │  │
│  │   - 記憶の保存、減衰、活性度、統合 Worker (Memory Core)               │  │
│  │   - ナレッジマップ・有向グラフ探索 (Graph Core)                       │  │
│  │   - FTS5 全文検索・Ollama ベクトル検索 (Retrieval Core)               │  │
│  │   - トークン予算制御・ペルソナ注入文生成 (Persona Core)               │  │
│  │                                                                       │  │
│  │  [データ永続化・品質保証層]                                           │  │
│  │   - SQLite / Ladybug DB へのスキーマ整合性                            │  │
│  │   - 入出力エンコーディング（UTF-8 保証、Windows での文字化け防止）   │  │
│  │   - 応答レイテンシ、トークン上限の厳格遵守                            │  │
│  └───────────────────────────────────────────────────────────────────────┘  │
└─────────────────────────────────────────────────────────────────────────────┘
```

### In-Scope（システム要求の対象）
システムが実行時にアクター（利用者または AI エージェント）に対して提供する**観測可能な振る舞い・入出力契約・データ品質・非機能特性**。
- MCP ツールやフックの入出力仕様（入出力データフォーマット、エラーハンドリング）
- 記憶の蓄積・想起・検索・減衰アルゴリズムの振る舞い
- データベース（SQLite / Ladybug DB）のデータ整合性、文字コード保証（UTF-8）
- Web ダッシュボードの検索・グラフ表示・操作性・トースト通知

### Out-of-Scope（システム要求ではないもの）
ソフトウェア実行時の振る舞いではなく、**開発・保守・環境構築・リポジトリ構造の都合**による作業。
- リポジトリの特定フォルダ（ルート直下か、`skills/` 配下か）へのスクリプト配置・移動
- アーキテクチャ刷新に伴い不要となったファイルシステム上の空ディレクトリ（`blobs/`, `logs/`）の削除
- 開発者向けドキュメントや規約の整備・更新
- 依存パッケージのインストールや仮想環境構築スクリプト自体のファイル管理

## 3. システム要求判定クライテリア (Decision Criteria)

開発指示や改修要望を受けた際、どの文書種別（`NEED` / `REQ` / `ADR` / コミット）で扱うべきかを判定するフローチャートと基準マトリクス。

### 判定フローチャート

```text
[開発指示・要望の発生]
       │
       ▼
【Q1: 実行時ソフトウェアの振る舞い・入出力契約・データ品質の変更か？】
  ├─ No ──► 【Q2: リポジトリ構成・アーキテクチャ方針の決定・変更か？】
  │                ├─ Yes ──► [ADR (docs/decisions/)] または直接作業・コミット
  │                └─ No  ──► [Chore / 開発作業]（文書起票不要、直接実装・コミット）
  │
  └─ Yes ─► 【Q3: 抽象的な背景・動機・ユーザー課題から始まるか？】
                   ├─ Yes ──► [NEED 起点 (パスA)]
                   │           └─ NEED-xxxx ──► REQ-yyyy ──► SPEC ──► DSN
                   │
                   └─ No  ──► [REQ 起点 (パスB)]（具体的機能・バグ修正・非機能品質）
                               └─ REQ-xxxx (depends_on: []) ──► SPEC ──► DSN
```

### 判定マトリクス

| 指示内容・事象の例 | 分類 | 推奨起票先 | 理由 |
|---|---|---|---|
| 「Windows環境でフックを通すと日本語が文字化けするのを防ぎたい」 | **システム要求**<br>(欠陥修正・品質) | `REQ` 起点<br>(または `NEED-0002`) | システム外部境界での入出力契約（UTF-8）とデータ完全性に関わる振る舞いであるため。 |
| 「想起グラフで同一プロンプトのノードが集約されて見やすくなってほしい」 | **システム要求**<br>(ユーザー課題・機能) | `NEED` 起点<br>(`NEED-0003`) | 利用者がダッシュボードを通じて観察する機能・UI表現に関する要望であるため。 |
| 「ルートにある setup.sh や setup.ps1 をスキルの scripts/ 配下に移動したい」 | **リポジトリ構成管理**<br>(Refactoring / Chore) | `ADR` 起点<br>(または直接作業) | ソフトウェアの実行時契約ではなく、リポジトリの資産配置・整理に関する内部都合であるため。 |
| 「旧アーキテクチャで使っていた blobs/ や logs/ フォルダを自動生成しないようにしたい」 | **デッドコード整理**<br>(Chore / Cleanup) | `REQ` 起点 (パスB)<br>または直接コミット | セットアップコード内の不要ロジック削除であり、独立したユーザー要求ツリーを組むには過剰。 |
| 「エージェント間通信のプロトコルを REST から JSON-RPC 2024-11-05 に移行する」 | **アーキテクチャ決定**<br>(Architectural Decision) | `ADR` 起点 | システム全体に影響する設計・方針決定であるため。 |

## 4. 外部システムインターフェースの管理方針 (External Interface Management)

Cursor IDE、AI エージェント、外部推論基盤（Ollama）など、外部システムとの境界をまたぐインターフェース（外部 IF）については、専用の種別を新設せず、既存のドキュメント階層に以下のようにマッピングして管理する（詳細は `docs/decisions/ADR-0005.md` 参照）。

```text
[外部アクター]           docs/actors/ACT-xxxx.md
       │                相手システム（Cursor IDE、Ollama等）の役割・責務・相互作用
       ▼
[インターフェース契約]   docs/specifications/SPEC-xxxx.md  ★外部IF仕様書（ICD）
       │                通信プロトコル、入出力スキーマ、エラー表現、制約
       ▼
[接続アーキテクチャ]     docs/design/DSN-xxxx.md
                        ポート＆アダプタ構造、リトライ、タイムアウト、フォールバック
```

### 外部 IF 仕様の記述ルール
- **記録先**: `docs/specifications/SPEC-xxxx.md` に集約する。
- **タグによる識別**: フロントマターに `tags: [interface, external, <対象名>]`（例: `[interface, external, hook]`, `[interface, external, mcp]`, `[interface, external, ollama]`）を付与する。
- **仕様の観点**:
  - **提供 IF（Inbound）**: Hook 受信仕様、MCP Server ツール仕様、Web API 契約など、自システムが提供する完全なスキーマ・契約を記述する。
  - **利用 IF（Outbound）**: Ollama 埋め込み API など、相手方が提供する IF については、本システムが依存するサブセットおよび異常系ハンドリング契約を記述する。

## 5. 本書の位置づけと今後の拡張 (Traceability & Schema Evolution)

1. **現行の運用 (ADR-0004 準拠)**:
   - 本書は `docs/` 直下に配置され、スキーマ検証（`scripts/validate_docs.py`）をパスしつつ、システム全体の目的と境界を定義する「正本」として機能する。
2. **将来の拡張（案C）への道筋**:
   - プロジェクトの成熟に伴い、ドキュメントスキーマに最上位の `vision` や `purpose`（例: `docs/vision/VIS-0001.md`）を新設して厳格な YAML バリデーション下に統合する検討を保留（On-hold）として維持する。
